- 2026-07-19 — Phase 2: **Classes, encapsulation & properties** — why properties exist (public field = unprotectable invariant; C# rejects Java-style get/set ceremony). Hand-written backing field + validation in the accessor; `value` as the implicit setter parameter. **Key idiom: route the constructor through the setters** so construction can't bypass validation. Property vs method decision (`IsExpensive` = adjective/cheap/side-effect-free → property; action/args/expensive → method). `ArgumentOutOfRangeException` + `nameof(value)` over bare `ArgumentException`. Named constants over magic numbers. Built & refactored `Product`.
- 2026-07-19 — Phase 2: **Constructors in depth** — chaining with `: this(...)` (chained ctor runs FIRST, then the body) for DRY construction; **writing any ctor removes the free parameterless one** (so `new Product { ... }` won't compile — an object initializer is shorthand for `new Product() { ... }` and still needs a ctor to call); object initializers run **after** the ctor and go **through the setters**, so accessor-level validation still protects them. `init` = "settable at creation, immutable after" — the sweet spot for identity. Forward pointer: `required` (Phase 4) exists to close the "initializer lets but doesn't force" gap. **Edge case mastered:** if a ctor throws, `new` never returns a reference → the half-built object is unreachable & GC'd; construction is all-or-nothing. Caveat: **don't let `this` escape a constructor.**
- 2026-07-19 — Phase 2: **`static`** — member belongs to the *type*, one copy for the process lifetime. Static field vs the cleaner `public static int X { get; private set; }` (world reads, class writes). Statics are shared across the **whole hierarchy** (a `DigitalProduct` increments `Product`'s counter via `base`). Danger of mutable static state: global state, hidden dependency, test leakage, **not thread-safe**. Walked the lost-update race step-by-step (`count++` = READ→ADD→WRITE; two threads both read 5, both write 6, one increment silently lost). Fixes named for Phase 4: `Interlocked.Increment`, `lock`.
- 2026-07-19 — Phase 2: **Inheritance** — `:` syntax; **constructors are not inherited**, derived must call `: base(...)` (base runs first). `virtual` = "here's a default, replace if you want" (optional override); `abstract` = "no body, you MUST implement" (abstract class only, can't be instantiated); `override` = the act of replacing. **C# is non-virtual by default** (deliberate: allowing override is a contract) — contrast with Java. `base.X` to extend rather than replace. `sealed` stops the chain. **`override` vs `new`:** override = real polymorphism (actual object type decides); `new` merely *hides* (declared reference type decides) → baffling bugs. Over-use warning: inherit only for genuine "is-a" + polymorphism, not code reuse (fragile base class). Built `DigitalProduct : Product` with `public override ShippingCost`.
- 2026-07-19 — Phase 2: **Abstract classes vs interfaces** (concept delivered; task pending) — abstract class = "is-a" + shared state/implementation/ctors; interface = "can-do", pure capability contract, no state, members implicitly `public`. Decision criteria: single-inheritance constraint (one base, many interfaces), need to share state?, are implementers related?, versioning cost (adding to an interface breaks every implementer). Heuristic: **"is-a" → abstract class, "can-do" → interface**; when both fit, prefer the interface (keeps the inheritance slot free, enables DI/testing → "program to an interface"). Default interface members noted as a versioning escape hatch, not a reason to stop thinking in is-a/can-do.
- 2026-07-19 — Phase 2: **Polymorphism, casting, `is`/`as`** — every reference has **two types**: the **compile-time (declared) type decides what you may call**, the **runtime type decides which implementation runs** (virtual dispatch). Upcast (derived→base) implicit & always safe; downcast explicit & can throw `InvalidCastException`. `is` with a **type pattern** (`if (p is DigitalProduct dp)`) is the modern default — test+cast+scope in one; `as` returns `null` instead of throwing; raw `(Derived)x` only when the type is provable. Type patterns compose in `switch`. **Design smell noted:** heavy `is`/downcasting usually means behaviour that belongs inside the class as a `virtual` member (`ShippingCost` = the good pattern; `DownloadUrl` = legitimate `is` use). Implemented a polymorphic `Product[]` loop + `IDiscountable` on `Product`.
- 2026-07-19 — Phase 2: **DRILL — `PaymentMethod` hierarchy** (self-requested extra practice; built from a blank file). `abstract class PaymentMethod` (bodyless `abstract ProcessPayment()`, `virtual TransactionFee` default 2%), `CreditCardPayment : PaymentMethod, IRefundable` (inherits the fee default), `CashPayment : PaymentMethod` (overrides fee to 0, deliberately NOT `IRefundable`), polymorphic `PaymentMethod[]` loop + `is IRefundable r` capability check. **All four concepts implemented correctly on the first attempt.** Learned: **Template Method** — `Summary()` is non-virtual but calls abstract members, so base-class code dispatches down into derived implementations. Learned: base class must be listed **before** interfaces in the base list. Fresh analogy that landed: employees/roles (can't hire "an Employee"; `DoWork` abstract; `CalculateBonus` virtual; `IDrivesCompanyCar` cuts across roles).
- 2026-07-20 — Phase 2: **`object` fundamentals — `Equals` / `GetHashCode` / `ToString`.** Every type inherits them and **the defaults are usually wrong for domain types**: `ToString()` prints the type name (useless in logs), `Equals()` is **reference** equality for classes, `GetHashCode()` follows identity not data. **The contract: if `a.Equals(b)` then `a.GetHashCode() == b.GetHashCode()` — `Dictionary`/`HashSet` find by hash bucket first, then equality, so breaking it makes lookups silently fail.** Saw **`CS0659`** live (compiler warns when you override `Equals` without `GetHashCode`) and reported the code — good error-reading habit. Implemented `ToString()`, `Equals(object?)` via the `is Product other` type pattern, and `HashCode.Combine(...)` (don't hand-roll hash math). **Key gotcha learned: overriding `Equals` does NOT change `==`** — `==` is an *operator*, defaulting to reference comparison for classes unless explicitly overloaded, so `a.Equals(b)` and `a == b` can disagree (predicted this correctly). Two further defects raised for fixing: `is Product` matches **subclasses** (a `DigitalProduct` compares equal to a `Product`) → compare exact `GetType()`; and `Product` is a **mutable hash key** (public setters) → mutating after insertion makes the object unfindable in its own `HashSet`.
